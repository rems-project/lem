# 02 — Comment text is decoded as Latin-1: non-ASCII characters in `.lem` comments come out mis-encoded (`§` becomes `Â§`) on every backend

Target: `rems-project/lem`, `src/lexer.mll`. State: **Draft**, not
filed. Drafted 2026-10-03. No patch branch (no fix exists yet).

## Affected code (upstream `3802cb0`)

- `src/lexer.mll:265-271`, rule `comment`: every comment fragment becomes
  `Ast.Chars (Ulib.Text.of_latin1 i)` (`:268`, `:269`, `:271`), so each
  byte of a UTF-8 sequence becomes one Latin-1 code point. The backends
  then write the text out as UTF-8.
- For contrast, string literals are checked as UTF-8 (`:285-289`, "String
  literal is not valid utf8") and print correctly.
- `src/lexer.mll:61` (`let r = Ulib.Text.of_latin1`) is the same decoding
  used for other tokens; the Cerberus record cited this line.

lem-lean's `src/lexer.mll` is unchanged in these rules (its only
difference is extra keywords; the comment rule is at lines 278-284
there). The defect is present in lem-lean too.

## Classification

**TRUE BUG.** Lem treats source text as UTF-8 (string literals must be
valid UTF-8), but comments are decoded as Latin-1, so a UTF-8 source file
round-trips into different characters. The output is still valid in each
target language (comments only), so the effect is corrupted documentation,
not wrong code.

## Observed vs expected

Observed: `§` (`c2 a7`) is written as `Â§` (`c3 82 c2 a7`) in comments on
all four backends; the string literal on line 9 is correct. Expected:
comment text written out byte-for-byte as in the source.

## Impact

Any Lem development whose comments contain non-ASCII text gets mis-encoded
comments in every generated file. In the Cerberus sources this affects the
`§` used for C standard clause references: the Cerberus record counted
`Â§` in 28 files of the OCaml tree generated by pristine upstream Lem
`3802cb0`. The generated code is unaffected.

## Proposed remedy

Decode comment fragments as UTF-8 (`Ulib.Text.of_string`, with the same
`Malformed_code` diagnostic as string literals, or a fallback to Latin-1
only for invalid UTF-8 so that old Latin-1 sources keep working). The
rules at `:268-271` are the minimum; `Ast.Ws` whitespace (`:175`) and
other tokens built with `r` hold ASCII in practice. Generated output for
ASCII-only sources is unchanged.
