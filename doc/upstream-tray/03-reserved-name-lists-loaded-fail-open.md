# 03 — A missing `<target>_constants` file is silently treated as empty: renaming is disabled and Lem emits reserved words as identifiers

Target: `rems-project/lem`, `src/initial_env.ml`. State: **Draft**, not
filed. Drafted 2026-10-03.

No patch branch. A fix (below) was built and checked on a local branch on
`3802cb0`; that branch was deleted, as this tray prepares reports only,
not pull requests ([USER 2026-10-03] ruled out upstream-PR writing and had the branches deleted).

## Affected code (upstream `3802cb0`)

`src/initial_env.ml:116-121`:

```ocaml
let read_target_constants lib_path targ =
  match targ with
    | Target_ident -> NameSet.empty
    | Target_no_ident targ' -> (try 
        read_constants (lib_path ^^ (non_ident_target_to_string targ' ^ "_constants"))
      with _ -> NameSet.empty)
```

called from `src/main.ml:276`. The library ships `coq_constants`,
`hol_constants`, `isabelle_constants` and `ocaml_constants`.

lem-lean's copy differs: it carries the fix (commit `8c3a4ca`,
2026-09-28), including its Lean target.

## Classification

**TRUE BUG** (fail-open error handling). Any failure to read the file —
a wrong `LEMLIB`, an incomplete install, a library copy without the file —
is swallowed, and Lem exits 0 with output that the target compiler
rejects or, worse, accepts with a different meaning.

## Reproducer

`kw.lem` (`done` and `to` are OCaml keywords listed in `ocaml_constants`
but not Lem keywords):

```lem
open import Pervasives

let done (to : nat) : nat = to + 1
```

`lib-no-constants/` is a copy of upstream `library/` without
`ocaml_constants`.

## Observed vs expected

Observed: no diagnostic, exit 0, invalid OCaml. Expected: an error naming
the missing file, as for any other missing library file.

## Impact

The renaming pass is the only protection against target keywords and
reserved names. When it is silently off, the result is invalid output
(as here) or, for the prover targets with long lists (HOL4: 763 names,
Isabelle: 426), output that may elaborate against the wrong constant. The
fork hit this for real on its Lean target. The lem-lean record
(`doc/lean-backend/2026-09-28_linksem-findings.md` §B10) says: "It
happened for real (B12): seven parity probes failed to compile in one
suite run with exactly those errors." §B12 gives the cause: a relative
`LEMLIB` that was wrong for recipes that change directory.

## Proposed remedy

The fix: for hol, ocaml, isabelle and coq, a missing file or a
`Sys_error` while reading it is a fatal error naming the file; tex, html
and lem keep the empty set. Verified there: `make` (bin/lem, every library
backend, ocaml-lib and its tests) succeeds and the 145 library files Lem generates
(29 OCaml, 29 HOL4, 29 Isabelle, 58 Coq: those marked "Generated by Lem") are
byte-identical to `3802cb0`'s.
